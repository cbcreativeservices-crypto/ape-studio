Topic Foundations: Game Audio

In a film, the sound never changes. A door closes at the same moment every time. A game is different. The player decides when to open the door, where to walk, and whether to fight or hide. So how can sound be ready for moments that nobody can predict?

The game asks for a sound only when something happens. When a character jumps, the game code sends out a name, for example "jump". That request is called an audio event. The sound designer decides which sound plays for that name, in a separate program between the sound files and the game. That program is called middleware. So the designer can change a sound without changing the game code.

The first problem appears with footsteps. A character takes a very large number of steps. If one recording plays for every step, the ear soon notices the exact repeats. This is called the machine-gun effect. So designers record several versions, and the software picks one at random, often with a small change in pitch.

The sound must also come from the right place. The game knows where each sound source is and where the player's virtual ears are. As the distance grows, the sound becomes quieter. When a wall stands between them, the sound also loses high frequencies. That is called audio occlusion. Rooms can also add their own echoes.

Music must change too, because nobody knows when a fight will start. One common method writes the music as several parts that play together in time. The game adds parts as the action becomes more intense, and removes them when it becomes calmer. This is called vertical layering. Another method changes the order of short sections, usually at the next point that fits the beat.

To make these choices, the sound system needs to know what is happening. The game sends numbers that change all the time, such as speed or health. It also sends named situations, such as fighting or underwater. Each one is called an audio state, and many sounds change together with it. The mix also adjusts itself, for example lowering the music when someone speaks.

All of this must fit inside limits. Sound gets only a part of the game's memory and processing time. So sounds are stored in groups, and each group loads when its part of the game starts. When too many play at once, the least important ones stop first. Spoken lines also need their own system, because the player's choices can change what a character says next.

The flashcards explain each part in detail, from the first event and the people and tools that build it, to the final tests. By the end, you will know how a game decides which sound to play, where it seems to come from, and how it changes as the player acts.
