Topic Foundations: Game Audio

Imagine playing a game. You choose when to open a door, where to walk, and whether to fight or hide. The game cannot know your next choice. So how can sound be ready for moments that nobody can predict?

Some background sounds play the whole time, but most game sounds start only when something happens. When a character jumps, the game code sends out a name, for example "jump". That request is called an audio event. The sound designer decides which sound plays for that name, in a program between the sound files and the game. That program is called middleware. The designer can then change a sound without new game code. An implementer connects each event to its action in the game, and testers check that each sound plays correctly.

Footsteps show the first problem. A character takes many steps. If the same recording plays for each one, the ear soon notices the exact repeats. This is called the machine-gun effect. So designers record several versions, and the software picks one at random, often with a small change in pitch.

The sound must also come from the right place. The game knows where each sound source is. It also knows the point the player hears from, usually the character or the camera. As the distance grows, the sound becomes quieter. When a wall is between them, the sound becomes even quieter and loses high frequencies. That is called audio occlusion. Rooms can also add their own reflections.

Music must change too, because nobody knows when a fight will start. One common method writes the music as several parts that play together in time. The game adds parts as the action becomes more intense, and removes them when it becomes calmer. This is called vertical layering. Another method changes the order of short sections, usually at a point that fits the beat.

The sound system also needs to know what is happening. The game sends numbers that change all the time, such as speed or health. It also sends named situations, such as fighting or underwater. Each one is called an audio state, and many sounds change together with it. The game can also change the mix automatically, for example lowering the music when someone speaks. What characters say can also change with the player's choices.

All of this must fit inside limits. Sound gets only a part of the game's memory and processing time. So sounds are stored in groups, and each group loads when its part of the game starts. When too many sounds play at once, the least important ones usually stop first.

The flashcards explain each part in detail, from the first event to the final tests. By the end, you will know how a game decides which sound to play, where it seems to come from, and how it changes as the player acts.
