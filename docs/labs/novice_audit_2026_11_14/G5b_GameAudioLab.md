| Where a beginner sticks | (1) The burst list groups the impacts ("impact × 4") but the total says "TAKEN 9", so the five listed lines and the 9 do not obviously match. (2) The ordering rule ("least important first") only makes sense if you know loops count as less important than an impact; the SOUNDS tray says so in its headings ("LESS IMPORTANT THAN AN IMPACT" / "PROTECTED: THEIR VOICE IS NOT TAKEN"), which is good, but the card does not repeat it. (3) BUDGET moves in steps of 4 (16 → 12 → 8 → 4 → … → 1), so "set BUDGET to 8" takes two taps and the learner sees 12 first. (4) The MEMORY maths block (G5's point) sits directly under the burst experiment and competes with it. |
| What works | A results card that appears in the same place every time; plain verbs (STOLEN, REFUSED, went virtual, came back); the log teaching the rule at the moment it fires; protected vs less-important groups in the tray headings; a check whose wrong answer is corrected with the rule. |
| Suggestions | 1. Add a line for what was kept: "Kept: ALARM (protected)". S. 2. Make the count match the list ("TAKEN 9 = 5 loops + 4 impacts"). S. 3. Repeat the tray's ranking on the card ("Order: least important first (loops) · then oldest · protected never"). S. 4. Show the budget value under the FEWER / MORE keys while pressing, or step 16 → 8 → 4 → 2 → 1 so the step's target is one tap. S. 5. Fold MEMORY (as G5 said). M. |
| Hobbyist | Exactly sampler polyphony; they will enjoy setting the budget to 1. |

## Page 19 · Testing and fault finding (baseline run; all five faults found and fixed)

| Field | Notes |
|---|---|

| Baseline | The healthy pattern appears exactly as step 2 promises: "GAME · TRIGGER door opened → GAME · EVENT Play_Door posted by DOOR → START · Door · door_open.wav → EFFECTS bus (not heard: sound is off) → START · Door · rattle, 1 s later… → STOP · Door i88 ended". With sound off, the log carries everything. |
| Fault 1 · the door | Log: "FAULT · Door: the file "door_open_v2.wav" is NOT IN THE BUILD. The event was posted, but this layer cannot play" (G5 predicted the repeat of page 6; it is the same fault, word for word). FIX → DOOR FILE → door_open.wav → "FIXED 1". |
| Fault 2 · the guide's voice | The best fault of the five: there is NO fault line. The learner has to notice that the guide's line went to the wrong place ("START · Guide: greeting · line · vo_guide_greeting_EN.wav → EFFECTS bus") and that no DUCK line followed. The card tells you what to look for ("Read which bus the line went to."). FIX → VOICE BUS → DIALOGUE → fixed. |
| Fault 3 · the footsteps | Log: "Footstep · step take 1 of 4" on each step (the take number is the evidence). FIX → TAKES → VARIATION · ON → fixed; the log then confirms "MIX · SETTING variation (use every take): ON". |
| Fault 4 · the surface | Log: "TRIGGER foot contact · GUIDE · SWITCH surface = stone" while the card says the guide stands on wood: the learner compares log and picture, which is exactly the method. FIX → SURFACE SWITCH → FOR EACH CHARACTER → fixed. |
| Fault 5 · the loop | Log: "FAULT · GENERATOR 2 was removed but nothing stopped its loop: instance i109 is an ORPHAN, still playing with no owner". FIX → REMOVAL → STOP ITS LOOP did **not** mark it fixed: the orphan kept playing (PLAYING 2) and "1 fault is active" stayed. Trying to re-run gave "■ STOP first: a stray loop still holds generator 2." and the log "REFUSED · GENERATOR 2 is not placed again: its old loop, instance i109, still plays with no owner. ■ STOP silences it; then place the generator again". After ■ STOP and a re-run (add, on, remove): "GENERATOR 2 removed: its instance i109 is stopped and released with it" and "FIXED 5". The lab's own messages rescued me, but the card never says that fault 5 needs STOP + a re-run while faults 1-4 count as fixed the moment the setting changes. |
| Where a beginner sticks | (1) The FIX tray opens with the right tab already selected and ticked ("✓ VOICE BUS", "✓ TAKES"…): it gives the answer away, and a beginner may read the ✓ as "this one is fine". (2) Faults 1-4 count as fixed without re-running the action, although step 3 says "After a fix, run the same action again" (the rule is stated, not required). Fault 5 is the opposite (it requires STOP + re-run): inconsistent. (3) Pressing STEP three times quickly printed one START line and three STOP lines in the visible log: the pattern the page asks you to compare is easy to misread when taps are fast. (4) Faults 1 and 3 repeat earlier pages (6 and 9); that is fine as revision but the card does not say so (G5). |
| What works | A baseline before faults; "finding comes before fixing" enforced (FIX shows "every setting is correct now" until a fault is active); fault 2 and 4 make the learner compare evidence (bus name, surface name vs picture) instead of reading a FAULT line; the FAULTS / FIXED counters; the rescue messages in fault 5. |
| Suggestions | 1. Open the FIX tray on a neutral tab (or the list of five settings with no tab selected), and use ✓ only for "correct now". S. 2. Make every fault need the same proof: after the fix, ask for the action again and only then count it ("Run OPEN DOOR again to confirm"). S. 3. On fault 5's card, add the real step: "Fixing the setting does not stop a loop that is already orphaned: press ■ STOP, then repeat the action." S. 4. Say "you met this on page 6 / 9: try it without the hint" on faults 1 and 3 (G5). S. |
| Hobbyist | The page they will enjoy most: real debugging with a log, and two faults that need actual reasoning. |

## GAME AUDIO LAB · G5b verdict (pages 17 and 19, hands-on)

Both pages work fully with sound off: the burst card and the activity log carry every result in plain verbs (STOLEN, REFUSED, went virtual, ORPHAN). Page 17's three goals and page 19's five faults can all be completed by a careful beginner. The friction is small and fixable: the burst card does not name what was kept, its count does not match its list, the FIX tray pre-selects the answer, and the "run it again" rule is applied to one fault out of five.
