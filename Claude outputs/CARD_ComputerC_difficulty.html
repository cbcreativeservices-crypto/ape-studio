What C does

For every term, reads the term + its definition and assigns the level it truly sits at — beginner (foundational vocabulary), intermediate (applied working knowledge), or advanced (specialist / math / edge). It re-derives from scratch; the current tag is just the starting label.
Aim for a spread, never force a quota. The rule is explicit: the term's true level always wins — no promoting an easy term to advanced or demoting a hard one to beginner to even the numbers. A topic that genuinely can't spread gets flagged genuinely_skewed rather than faked.
Report-only: C returns one line per term (current → proposed + a short rationale) plus a per-topic summary. It writes nothing to the database.

The packet

START_HERE_ComputerC.md — the rubric + the anti-quota rule + return shape.
MANIFEST.json — 29 topic files, most-lopsided first.
items/*.jsonl — every term with its current tag + definition.
RETURN_SCHEMA_EXAMPLE.jsonl — the per-term line + topic summary line.

Flow back — and one thing I'll handle in QA

C returns → I QA the proposed levels (defensibility on a sample + sanity of each new distribution) → I package one guarded SQL run updating glossary_topics.difficulty → you apply.
The coupling I'll manage (not C's concern): difficulty is linked to quiz coverage — intermediate/advanced terms are meant to carry ~5 questions, beginner terms are flashcards-only. A re-tag can leave some newly int/adv terms without questions yet, and some newly beginner terms still carrying questions. Neither breaks the app (the quiz reads difficulty as a soft priority and the validation trigger only needs it non-null), but after applying I'll compute both cascades and hand you the follow-up — which terms now need questions authored, and which beginner-with-questions to leave or retire. So this re-balance is step 1; a small coverage-reconciliation plan follows it.
